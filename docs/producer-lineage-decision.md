# producer 可指认性——决策文档（已裁 2026-09-27）

> demo-protocol v0.3 缺口②的决策件。你的指令（2026-09-27）：「你思考下研究之后给我文档，我来决策利弊」。
> 问题：`lineage.producer` 指向站仓外的生成脚本，站侧无法用 git 追溯其内容/版本——「可指认」的最低要求是什么？
> 现状事实：首跑（时空语录）的 producer = `D:\skill-data\runs\project-lifecycle\20260927T162733-41bb\gen_spacetime_demo.py`——脚本实际存在 skill-data 的 run 目录里，但这条通路是首跑自行走的，协议没写。

## 先说白话：这是个什么问题

血统三要素里 `rev` 锚的是**站仓**的版本，`producer` 只是一个**路径字符串**。脚本在站仓外时，这个字符串指向的东西站里管不着：脚本被改了、删了、换机器了，路径还在但内容对不上——「可指认」就只剩一个空指针。要补的是：**拿什么保证这个指针指得到真实内容**。

## 选项与利弊

### A. run 目录归档明文化（+不走 run 记 sha256 兜底）

协议写明：走 run（project-lifecycle 体系）的提交方，producer 指 run 目录；不走 run 的提交方，lineage 补 `producer_sha256` 字段（脚本内容哈希）。

- **利**：零搬运（首跑已是事实，规范化现状）；run 目录天然 repo 外持久（与跨项目索引同一设计哲学：删库行存）；run_id 是现成的追溯 join key（台账/run.json 全套在）；skill-data 换机有 env.yaml 迁移路径。
- **弊**：**绑定 skill-data 体系的寿命**——若你未来弃用这套体系或换机不迁，指针断；不走 run 的外部提交方（假想的第三方）仍只有哈希、拿不回脚本内容；「可指认」强度 = skill-data 目录的寿命，而非 git 的寿命。

### B. 一律记 producer_sha256（最简统一）

lineage 新增 `producer_sha256`（必填或强烈推荐），不依赖任何外部体系。

- **利**：协议自足——不赌 skill-data 的寿命；一个字段解决；可比对（外部项目还在时能验「就是那个脚本」）。
- **弊**：**只能证明「曾经是那个哈希」**——脚本事后被改/删，内容永久不可复原；对外部提交方多一个填写项（摩擦小但非零）；与 §8 向后兼容承诺有缝：老 demo 无此字段，若设必填则只对新提交生效（口径要写清）。

### C. producer 脚本副本归档进站仓

`demos/<slug>/producer.py`（或整目录）随三件套进站 git。

- **利**：**可指认性最强**——克隆站仓即得全部血统，git 全量追溯，站仓自足，与 skill-data 寿命无关。
- **弊**：站仓收外部生成代码，与定界「site 不管落码，只做承载+协议+验收」有张力；每 demo 多一件提交物+站侧审查面（脚本里的 key 处理、脏逻辑都会进公开仓——上云后是泄漏面）；站仓体积随 demo 数线性涨。

### D. 混合分级（A 为默认 + 里程碑 demo 走 C）

默认 A；仅「里程碑级 demo」（如首页精选、对外演讲引用的）要求脚本副本进站仓。

- **利**：日常零摩擦，重要节点血统最强。
- **弊**：「里程碑」无客观判据→执行时扯皮；两套规则=协议复杂度翻倍；首版没有里程碑案例，等于预先设计。

## 判据问题（决定你选哪个）

1. **skill-data 的寿命预期**：它是你的终身跨项目体系，还是阶段性试验品？终身 → A 的绑定风险趋零；试验品 → B/C 权重升。
2. **外部提交方会是谁**：可预见的将来只有你自己（+你的 agent）走全链？还是真会有第三方？只有自己 → A 的事实通路已够；有第三方 → 需要 B 的自足字段。
3. **站仓公开（上云）后，愿不愿意外部脚本进仓**：愿意 → C 可行；不愿意 → C 出局，只剩 A/B/D。

## 推荐（agent 侧，供参考不作数）

**A**：它把已经发生的事实升格为规范（零成本），sha256 兜底字段覆盖不走 run 的场景；C 的最强可指认对 solo 自用阶段是过度供给——等你真有「第三方提交」或「里程碑 demo」出现时，再按 D 升级不迟（协议 §8 向后兼容，新增字段一律可选，升级零破坏）。

## 决策栏
